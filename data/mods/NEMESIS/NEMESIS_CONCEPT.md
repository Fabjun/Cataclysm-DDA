# NEMESIS Mod — System Concept Document

> **Purpose:** This document is a self-contained reference for the NEMESIS mod.
> It is written to bring any collaborator (human or AI) up to full context in one read.
> When starting a new chat session about this mod, paste this document in first.

---

## 1. What the Mod Does

When a player character dies in Cataclysm: Dark Days Ahead, the game writes a save file containing everything about that character — their stats, skills, equipped gear, bionics, mutations, and cause of death. The NEMESIS mod reads that file and uses it to generate a hostile NPC: the Nemesis.

The Nemesis is not a generic survivor. It wears what the dead character was wearing, carries what they had in their pockets, and bears wounds proportional to how they died. Its body shows the mark of its death: a character who burned looks deformed; one who drowned is bloated; one killed by a mycus infection carries fungal traits. It arrives on a delay — a weak character returns in days, a powerful one in months.

The Nemesis spawns passively into the world and does not pursue the player until provoked. Once the player lands a hit, it enters active hunt mode: it tracks using perception, noise, and memory of the player's last position. If it loses the trail long enough, it gives up and enters ambush mode — a lower-vigilance state where it can be re-triggered by proximity. Killing it drops a small memento item with the character's name, death cause, and a closing narrative line. One life only — it does not return.

## 2. Hard Rules

These rules are non-negotiable and must be followed in every session:

1. **Never touch any C++ source file.** The entire mod is JSON + Python. No exceptions.
2. **Write thorough English comments.** Every function and major JSON block must have comments clear enough for a new developer to understand structure and intent without reading surrounding code.
3. **Update the README after every feature addition.** The README is the player-facing contract.
4. **Never manually edit `nemesis_master.json` or any `nemesis_seed_*.json`.** These are always auto-generated by Python scripts and will be overwritten.
5. **Tier labels (T1–T4) are seeder-only.** They must never appear in gameplay EOC calculations. All hunt behavior derives from actual NPC stats (`u_val('intelligence')`, `u_val('perception')`, etc.), which work for both offline seeded characters and real Mode 2 player characters.

## 3. Two Modes

### Mode 1 — Offline (current focus, proof of concept)

The player runs Python scripts locally to generate Nemeses. Two workflows:

- **Cold-start seeding:** `python3 nemesis_seeder.py` generates synthetic characters without a real save file. Uses item pools and name lists to create fictional Nemeses at different strength levels.
- **Death conversion:** `python3 nemesis_launcher.py /path/to/character.sav` parses a real dead character's save file and converts them into a Nemesis.

Both workflows write per-character JSON files, then compile a single `nemesis_master.json` routing tree that the CDDA game reads.

**Status:** Feature-complete as a proof of concept. Several enhancements planned (see Section 8).

### Mode 2 — Async Multiplayer (scaffolding only, backend TBD)

Players upload their dead characters to a shared database. Other players download those characters to populate their own worlds — meaning the Nemesis hunting them is a real dead player from someone else's game.

**Key design constraints for Mode 2:**
- There are **no tier levels** in Mode 2. Real dead players have real stats, not tier labels.
- All gameplay behavior must derive from actual NPC stats to work correctly in both modes.
- Identity design (anonymous vs. username vs. token) is deferred until a backend is chosen.
- The client-side interface (`nemesis_sync.py`) is being designed now; HTTP calls are stubs.

**Status:** Interface design in progress. Backend not decided.

## 4. Technical Architecture

### Pipeline

```
Player death (.sav file)  OR  nemesis_seeder.py (synthetic)
        │
        ▼
nemesis_launcher.py           ← CLI entry point
        │
        ├─► nemesis_builder.py
        │     ├─ load_save_file()         read .sav (strips # comment lines)
        │     ├─ _load_memorial_log()     read companion .log file
        │     ├─ extract_*()              stats, gear, skills, bionics, mutations,
        │     │                           martial arts, spells, body-part HP ratios,
        │     │                           death location (OMT pos), death day
        │     ├─ detect_death_cause()     34 classifiers from player state + log
        │     └─ build_*()               faction, item groups, npc_class, npc_template
        │
        ├─► nemesis_eoc.py
        │     └─ build_per_char_eocs()    5–6 EOC dicts per Nemesis:
        │                                   spawn_check, spawn_success, death_notify,
        │                                   wounds EOC, effects EOC
        │                                   [+ death_echo EOC when death OMT is known]
        │
        ├─► writes nemesis_<name>.json    NPC JSON + EOC JSON, one file per character
        │
        └─► nemesis_eoc.compile_master()
              ├─ scan all nemesis_*.json
              ├─ build_hub_eocs()         group by anniversary date
              ├─ build_master_eoc()       single EVENT listener routes to day hubs
              ├─ build hunt system EOCs   TRACKER, ANNOUNCER, ACOUSTIC, REVENGE, FLAGS
              └─ writes nemesis_master.json
```

### Spawn Lifecycle

Each Nemesis has a global state variable `global_nemesis_spawned_<safe_name>`:
- `0` — unarmed; first routing call arms it and records `global_nemesis_char_start_<name> = time('now')`
- `1` — armed; all spawn gates are evaluated each time the master routes to this check
- `2` — spent; Nemesis has spawned or is dead; permanently skipped

Spawn gates (all must pass): spawn_lock == 0, delay elapsed, location match (indoor/outdoor), anniversary date match.

Spawn radius: 40–55 OMTs from the player. Wounds and effects applied immediately via `u_run_npc_eocs`.

## 5. Key EOC Objects

All defined in `nemesis_hunting.json` (effects/mutation) and built by `nemesis_eoc.py` (EOC logic).

### NEMESIS_MARK — mutation

Applied to every Nemesis NPC via its `npc_class` definition. Zero cost, not purifiable, `valid: false` (invisible to players). Sole purpose: identifies Nemesis NPCs reliably across all EOCs without per-character listeners.

Used as selector in:
- `EOC_NEMESIS_REVENGE_TRIGGER` → `u_has_trait: NEMESIS_MARK`
- `EOC_NEMESIS_TRACKER` → condition splits Nemesis path from avatar path

### NEMESIS_HUNTING — effect type

Permanent duration. **Presence = active pursuit.**

Added by `EOC_NEMESIS_REVENGE_TRIGGER` when the player hits the Nemesis. Removed on give-up. Can be re-added by hitting again (hit-based re-trigger, always available) or by proximity re-trigger from ambush mode.

### NEMESIS_OVR_DIST — effect type

Intensity = current overmap search radius in OMT units.
- Set to 30 (`_OVR_DIST_START`) on hunt arm
- Decremented by 3 (`_OVR_DIST_SHRINK`) per hot-trail tick
- Floor: 2 (`_OVR_DIST_MIN`)
- Set to 5 on give-up (ambush mode radius)
- Reset to 30 on ambush proximity re-trigger

### NEMESIS_FRUSTRATION — effect type

Intensity = consecutive cold-trail tick counter.
- +1 (`_FRUSTRATION_INCR`) per cold tick
- -2 (`_FRUSTRATION_DECR`) per hot tick (recovery faster than accumulation)
- Give-up condition: `intensity * 2 >= u_val('intelligence') + u_val('perception')`
- Reset to 0 on ambush proximity re-trigger

### NEMESIS_AMBUSH — effect type (IMPLEMENTED)

Permanent, intensity 1. Distinguishes post-give-up state from initial passive state.

Applied when frustration overflows (give-up). Removed when proximity re-trigger fires (player enters 5 OMT ambush radius). While present, the tracker runs a reduced-range proximity check instead of the full hunt loop.

## 6. Hunt State Machine

```
PASSIVE (spawned, no hunt effects)
    → player hits Nemesis → ADD NEMESIS_HUNTING, SET OVR_DIST=30

ACTIVE HUNT (has NEMESIS_HUNTING)
    Tracker fires every 60 min:

    Compute score:
        score = max(0, NPC_PER - omt_dist * 3) * 10   (vision)
              + noise_level * 2                         (acoustic, if not DEAF)

    Hot trail (score >= 15 OR dist <= 2 with score > 0):
        → update nemesis_last_tracked_pos to player pos
        → u_set_goal toward player
        → shrink OVR_DIST by 3 (floor 2)
        → reduce FRUSTRATION by 2

    Cold trail:
        Phase 1 — Disciplined Tracker (FRUSTRATION < (INT+PER)/4):
            → wander within OVR_DIST of nemesis_last_tracked_pos
            Feels like: searching the area where you disappeared

        Phase 2 — Animal Drift (FRUSTRATION >= (INT+PER)/4):
            → wander within OVR_DIST of NPC's own current position
            Feels like: erratic, unpredictable, unanchored from memory

        On phase transition: queue "The methodical feeling fades..." message

        → increment FRUSTRATION by 1
        → if dist <= dread_range: set global_nemesis_close flag (for dread messages)

    Give-up (FRUSTRATION * 2 >= INT + PER):
        → REMOVE NEMESIS_HUNTING
        → ADD NEMESIS_AMBUSH
        → SET OVR_DIST = 5 (ambush radius)
        → queue "The feeling of pursuit fades..." message

AMBUSH (has NEMESIS_AMBUSH, OVR_DIST=5)
    → player within 5 OMTs → REMOVE NEMESIS_AMBUSH,
                              ADD NEMESIS_HUNTING,
                              RESET OVR_DIST=30, RESET FRUSTRATION=0
                              queue "The feeling of pursuit returns..." message
    → player hits Nemesis → same re-trigger via NEMESIS_REVENGE_TRIGGER (always available)
```

### How behavior scales with stats (no tier labels in this calculation)

| INT+PER | Phase 1 duration | Phase 2 duration | Total hunt |
|---------|-----------------|-----------------|------------|
| 14–16   | 3–4 h           | 4 h             | ~8 h       |
| 20–24   | 5–6 h           | 5–6 h           | ~11 h      |
| 26–30   | 6–7 h           | 7 h             | ~14 h      |
| 32–40   | 8–9 h           | 8–9 h           | ~17–18 h   |

## 7. Dread System (IMPLEMENTED)

When the Nemesis is hunting (NEMESIS_HUNTING) and within its **dread range**, the player may receive an atmospheric warning — depending on their own stats.

**Dread range (derived from NPC stats — no tier involved):**
```
dread_range = max(3, (NPC_INT + NPC_PER) / 4)
```

**Player dread score:**
```
dread_score = player_PER + survival_skill * 2 + morale_bonus
morale_bonus = 2 if player morale > 0 else 0
```

**Messages:**

| dread_score | Message |
|---|---|
| >= 15 | "The hairs on the back of your neck stand on end. It's close." |
| >= 12 | "Something is wrong. Your instincts scream that you are not alone." |
| >= 9  | "You feel vaguely unsettled, as if a memory is pulling at you." |
| < 9   | silent |

Messages are per-Nemesis, not globally throttled. Multiple simultaneous hunters compound the dread.

## 10. Key Design Decisions

| Decision | Choice | Reason |
|----------|--------|--------|
| Hunt trigger | Hit-based only (damage from player) | Feels earned; the Nemesis reacts to being attacked, not to proximity |
| Nemesis lifecycle | One life — gone forever on death | Finality matters; the memento is the closure |
| Dread messages | Per-Nemesis, not globally throttled | Compounding fear from multiple hunters is intentional |
| Dread/wander scaling | Derived from NPC INT+PER stats | Works for both offline (seeded) and Mode 2 (real players); no tier dependency |
| Cold trail Phase 1→2 anchor | Last-known-player-pos → own position | Strong Nemeses feel like disciplined trackers; weak ones like angry animals |
| Phase transition threshold | FRUSTRATION >= (INT+PER)/4 | Halfway to give-up; scales naturally with the same stats already in use |
| Ambush radius | Fixed 5 OMTs | Simple, testable, does not depend on tier or stats |
| Mode 2 identity | Deferred | Backend not decided yet |
| Debug patch | Separate tool, not inline flags | Modifies generated JSON files, not source; must be reversible without recompiling |
| No C++ changes | Hard rule | The mod must be a pure JSON+Python content mod |

## 13. Debug Mode Reference

`nemesis_debug_patch.py` is a living tool — new modes are added as new features are implemented.

```bash
python3 nemesis_debug_patch.py apply                        # strips spawn gates, adds debug messages
python3 nemesis_debug_patch.py apply --mode hunt --mode state  # stack multiple modes
python3 nemesis_debug_patch.py apply --nemesis alice_0042   # apply to one Nemesis only
python3 nemesis_debug_patch.py restore                      # restores all .json from .bak files
python3 nemesis_debug_patch.py restore --verify             # restore + scan for leftover debug strings
```

**`--mode` flags (all implemented, stackable):**

| Flag | What it tests |
|------|--------------|
| `--mode hunt` | Injects NEMESIS_HUNTING + OVR_DIST=30 on all Nemeses at spawn — no hit required |
| `--mode ambush` | Injects NEMESIS_AMBUSH + OVR_DIST=5 — tests ambush state and proximity re-trigger directly |
| `--mode state` | Adds RECURRING EOC printing each Nemesis's state every minute (HUNTING/AMBUSH/PASSIVE, OVR_DIST, FRUSTRATION, OMT dist) |
| `--mode dread` | Lowers dread detection thresholds to guarantee all three message tiers fire at 1 OMT |
| `--mode death-echo` | Overrides death OMT positions to the player's current location — no travel required |
| `--nemesis <safe>` | Restricts the entire patch to one named Nemesis only |
